Worum geht's?

In der Industrie arbeitet niemand allein an einem Projekt – egal ob Software, SPS-Programm oder Dokumentation. Damit mehrere Leute gleichzeitig an denselben Dateien arbeiten können, ohne sich gegenseitig etwas kaputtzumachen, gibt es Git und GitHub.

🕓 Git = Versionsverwaltung

Git merkt sich jede Änderung an jeder Datei: wer, wann, was und warum. Jeder alte Stand lässt sich wiederherstellen.

🌐 GitHub = Treffpunkt

GitHub speichert das Git-Repository online. Dort schlagen wir Änderungen vor, prüfen sie gegenseitig und besprechen Aufgaben.

🏭 Auch in der Automatisierung

SPS-Projekte werden zunehmend mit Git versioniert, z. B. über das Version Control Interface im TIA Portal oder CODESYS Git. Was du hier lernst, brauchst du später im Job.

Dein Weg in 7 Schritten

Jeder Schritt wird automatisch auf GitHub erkannt und erscheint innerhalb von etwa einer Minute auf dem Live-Fortschritt. Die Reihenfolge ist nicht streng – aber so ist es am einfachsten:

Du brauchst nichts zu installieren. Alle 7 Schritte funktionieren komplett im Browser. Wer möchte, kann später auch mit Git auf dem eigenen PC arbeiten.

1 GitHub-Konto erstellen & anmelden

📝 Meilenstein „Angemeldet“

a) Konto erstellen (falls du noch keins hast)

  1. Öffne github.com/signup.
  2. Gib deine E-Mail-Adresse ein, wähle ein Passwort und einen Benutzernamen. Den Benutzernamen brauchst du gleich – merk ihn dir gut.
  3. Löse das Rätsel, gib den Code aus der Bestätigungs-E-Mail ein und wähle den kostenlosen Plan (Free).
  4. Richte die Zwei-Faktor-Authentifizierung ein – GitHub verlangt sie für alle, die Code beitragen: Profilbild oben rechts → Settings → Password and authentication → Enable two-factor authentication. Am einfachsten mit einer Authenticator-App auf dem Handy. Die Recovery-Codes sicher aufheben!

Tipp zum Benutzernamen: Du musst nicht deinen echten Namen verwenden. Erlaubt sind Buchstaben, Zahlen und Bindestriche. Wähle etwas, das du auch in ein paar Jahren noch in eine Bewerbung schreiben würdest 😉

b) Für die Klasse anmelden

Trag hier deinen Namen und GitHub-Benutzernamen ein. Danach öffnet sich GitHub mit einem fertig ausgefüllten Anmelde-Issue (ein Issue ist so etwas wie ein Ticket). Dort musst du nur noch auf Create klicken.

Dein Benutzername wird nur in diesem Browser gespeichert, damit die Anleitung dir passende Links anzeigen kann.

Super! 🎉 Klick auf GitHub unten auf Create (oder Submit new issue) – dann bist du angemeldet. Falls sich kein neuer Tab geöffnet hat: Anmelde-Issue hier öffnen ↗

Als Nächstes lädt dich @Yourworstdream ins Repository ein → weiter mit Schritt 2.

Datenschutz: Das Repository ist öffentlich. Gib nur deinen Vornamen und den Anfangsbuchstaben deines Nachnamens an – keine Adresse, Telefonnummer oder Ähnliches.

2 Einladung ins Repository annehmen

🤝 Meilenstein „Im Team“

Nach deiner Anmeldung fügt dich @Yourworstdream als Collaborator (Mitarbeiter:in) hinzu. Erst dann darfst du im Repository Branches anlegen und Pull Requests zusammenführen.

  1. Du bekommst eine E-Mail: „@Yourworstdream has invited you to collaborate on the Yourworstdream/FSTAUD25 repository“. Schau auch im Spam-Ordner nach.
  2. Klick auf View invitation und dann auf Accept invitation.
    Oder direkt: Einladung auf GitHub öffnen ↗
  3. Fertig! Dein Anmelde-Issue wird automatisch geschlossen, sobald die Einladung angenommen ist (kann bis zu 10 Minuten dauern).

Einladungen verfallen nach 7 Tagen. Wenn GitHub dir später anbietet, das Repository zu „forken“ (Fork this repository), hast du die Einladung noch nicht angenommen – dann nicht forken, sondern die Einladung annehmen.

3 Dein erster Pull Request: der Steckbrief

🌿 Meilenstein „Pull Request“

Auf dem Haupt-Branch main liegt immer der „offizielle“ Stand. Niemand ändert main direkt. Stattdessen legst du einen eigenen Branch (Abzweigung) an, arbeitest dort und schlägst deine Änderung mit einem Pull Request (PR) vor. Nach einem Review wird sie in main übernommen (Merge).

So geht's – komplett im Browser

  1. Klick auf den Knopf. GitHub öffnet sich mit dem richtigen Dateinamen teilnehmer/dein-benutzername.md und einer ausgefüllten Vorlage:

    📄 Steckbrief-Datei auf GitHub anlegen ↗

    Trag zuerst in Schritt 1b deinen Benutzernamen ein, dann ist der Dateiname automatisch richtig. Ohne Knopf: Ordner teilnehmer öffnen → Add file → Create new file.

  2. Passe den Inhalt an (Emoji, was du lernen willst, Lieblingsthema). So sieht die Vorlage aus:

    # Dein Name

- **Emoji:** 🤖
- **Das will ich lernen:** Mit Git und GitHub im Team arbeiten
- **Lieblingsthema in der Automatisierung:** SPS-Programmierung
  3. Klick oben rechts auf Commit changes…. Als Commit message z. B. Steckbrief von Dein Name.
  4. Wähle „Create a new branch for this commit and start a pull request“, nenne den Branch steckbrief-dein-benutzername und klick auf Propose changes.
  5. Auf der Seite „Open a pull request“: Beschreibung kurz ausfüllen und rechts bei Reviewers ⚙️ eine Person aus der Klasse auswählen. Dann Create pull request.

Geschafft! Dein PR erscheint unter Pull requests und auf dem Live-Fortschritt leuchtet 🌿 auf.

Der Dateiname muss genau dein GitHub-Benutzername sein (z. B. max-m.md) und im Ordner teilnehmer/ liegen. Bearbeite nur deine eigene Datei.

4 Review bekommen & mergen

✅ Meilenstein „Gemerged“

main ist geschützt: Ein PR kann erst übernommen werden, wenn eine andere Person ihn geprüft und freigegeben hat. Das Review kann drei Ergebnisse haben:

ErgebnisBedeutungWas du tust
✅ ApprovedAlles gut, freigegeben.Mergen (siehe unten).
💬 CommentAnmerkungen oder Fragen, keine Entscheidung.Antworten, ggf. ändern.
🔁 Changes requestedBitte erst etwas ändern.Änderungen nachreichen.

Änderungen nachreichen

  1. Öffne deinen PR → Tab Files changed → bei deiner Datei auf ⋯ → Edit file.
  2. Ändern, dann Commit changes… – diesmal direkt auf deinen Branch steckbrief-… committen.
  3. Der PR aktualisiert sich automatisch. Kein neuer PR nötig!

Mergen

  1. Sobald dein PR freigegeben ist, erscheint unten der Knopf Merge pull request. Klicken und mit Confirm merge bestätigen.
  2. Danach Delete branch – der Branch wird nicht mehr gebraucht.

Noch kein Review bekommen? Schreib einen Kommentar in deinen PR und erwähne jemanden mit @benutzername – die Person bekommt dann eine Benachrichtigung.

5 Selbst reviewen

👀 Meilenstein „Review“

Reviews sind das Herz der Teamarbeit: Vier Augen sehen mehr als zwei. Prüfe mindestens einen PR von jemand anderem.

  1. Öffne PRs, bei denen du als Reviewer eingetragen bist ↗ – oder einfach irgendeinen offenen PR einer anderen Person.
  2. Tab Files changed: Grün markierte Zeilen sind neu, rot markierte wurden entfernt.
  3. Zu einer bestimmten Zeile etwas anmerken: mit der Maus auf die Zeile → blaues + → Kommentar schreiben → Start a review.
  4. Oben rechts Review changes (bzw. Submit review) → Comment, Approve oder Request changes wählen → absenden.

✔️ Worauf achten?

  • Richtiger Ordner, richtiger Dateiname?
  • Rechtschreibung und Formatierung?
  • Stimmt der Inhalt fachlich?

🤝 Fair bleiben

  • Erst loben, dann Verbesserungen.
  • Konkret: „Zeile 3: …“ statt „passt nicht“.
  • Kritisiere die Sache, nie die Person.

💡 Profi-Trick

Mit dem Knopf „Suggest changes“ (±) im Zeilen-Kommentar kannst du eine Korrektur direkt vorschlagen – die andere Person übernimmt sie mit einem Klick.

6 Mitdiskutieren mit Issues

💬 Meilenstein „Diskussion“

Issues sind unsere Aufgabenliste: Fragen, Ideen, Fehler, Themen fürs Projekt. Jede:r kann sie erstellen und kommentieren.

  1. Öffne den Tab Issues und such dir ein Thema aus – z. B. eines der Wiki-Themen.
  2. Unten ins Kommentarfeld schreiben und Comment klicken.
  3. Eigenes Issue erstellen: New issue → Vorlage wählen, z. B. 🆘 Ich brauche Hilfe oder 🧩 Idee fürs Klassenprojekt.

7 Klassenprojekt: das Automatisierungs-Wiki

🚀 Meilenstein „Projekt“

Zusammen schreiben wir ein Nachschlagewerk zur Automatisierungstechnik. 12 Themen für 12 Leute – jede:r übernimmt eine Seite im Ordner projekt/themen/.

  • 01 SPS-Grundlagen
  • 02 Programmiersprachen nach IEC 61131-3
  • 03 Sensoren
  • 04 Aktoren & Antriebstechnik
  • 05 Pneumatik & Elektropneumatik
  • 06 Industrielle Bussysteme
  • 07 IO-Link
  • 08 OPC UA & Industrie 4.0
  • 09 HMI & Visualisierung
  • 10 Regelungstechnik & PID-Regler
  • 11 Sicherheitstechnik
  • 12 Robotik & Handhabungstechnik

Ablauf

  1. Thema reservieren: Öffne das passende Themen-Issue, schreib „Ich übernehme das“ und trag dich rechts unter Assignees → assign yourself ein. Wer zuerst kommt …
  2. Seite anlegen: Neue Datei mit Vorlage öffnen ↗ und den Dateinamen anpassen, z. B. 03-sensoren.md. Die Vorlage liegt auch unter projekt/VORLAGE.md.
  3. Committen auf einen neuen Branch, z. B. thema/03-sensoren, und einen PR erstellen. Schreib in die Beschreibung Closes #<Nummer des Themen-Issues>.
  4. Inhaltsverzeichnis: Trag im selben Branch deinen Namen in die Tabelle in projekt/README.md ein. Weil das alle machen, gibt es hier vermutlich einen Merge-Konflikt – perfekt zum Üben!
  5. Review & Merge wie in Schritt 4. Sobald dein PR mit Änderungen in projekt/ gemerged ist, zündet 🚀.

Die Seiten dürfen gern mit der Zeit wachsen: Wer eine Seite verbessern will, macht einfach einen neuen Branch und PR.

So arbeiten wir zusammen

Jede Änderung – egal wie klein – läuft nach demselben Muster, dem sogenannten GitHub Flow:

🧩IssueAufgabe beschreiben
🌿Brancheigene Abzweigung
💾CommitsÄnderungen speichern
📬Pull RequestÄnderung vorschlagen
👀Reviewgegenseitig prüfen
✅Mergein main übernehmen

Unsere Teamregeln

  1. Nie direkt auf main. Immer Branch + Pull Request.
  2. Ein Branch = ein Thema. Kleine PRs werden schneller geprüft.
  3. Gute Commit-Nachrichten, die sagen, was sich geändert hat.
  4. Vorher aktualisieren: Vor dem Start neuesten Stand von main holen.
  5. Nur eigene Dateien bearbeiten – außer es ist abgesprochen.
  6. Respektvolle Reviews. Sachlich, konkret, freundlich.
  7. Keine Passwörter oder privaten Daten – das Repo ist öffentlich.
  8. Nach dem Merge den Branch löschen.

Branch-Namen

Kurz, klein geschrieben, mit Bindestrichen: steckbrief-max-m, thema/03-sensoren, fix/tippfehler-sps.

Merge-Konflikte verstehen und lösen

Ein Konflikt entsteht, wenn zwei Leute dieselbe Stelle einer Datei unterschiedlich geändert haben. Git weiß dann nicht, welche Version richtig ist – das musst du entscheiden. Das ist ganz normal und kein Fehler!

Git markiert die Stelle so:

| 02 | Programmiersprachen nach IEC 61131-3 | Lena K. |
<<<<<<< thema/03-sensoren
| 03 | Sensoren                             | Jonas M. |
=======
| 03 | Sensoren                             | Aylin S. |
>>>>>>> main
| 04 | Aktoren & Antriebstechnik           |          |

Oben (bis =======) steht deine Version, unten die Version aus main. Du löschst die Markierungszeilen und behältst, was richtig ist – manchmal beides.

Im Browser lösen

  1. Im PR steht „This branch has conflicts that must be resolved“. Klick auf Resolve conflicts.
  2. Bearbeite die markierte Stelle: Zeilen mit <<<<<<<, ======= und >>>>>>> löschen, richtigen Inhalt stehen lassen.
  3. Mark as resolved → Commit merge. Fertig – der PR kann jetzt wieder gemerged werden.

Konflikte vermeiden: Kleine PRs, schnell mergen, und wenn im PR Update branch angezeigt wird, draufklicken – dann holt GitHub den neuesten Stand von main in deinen Branch.

Für Fortgeschrittene: Git auf dem eigenen PC

Im Browser kommst du durch alle 7 Schritte. Für größere Projekte ist es aber praktischer, lokal zu arbeiten. Drei Möglichkeiten:

🖱️ GitHub Desktop

Am einfachsten, ohne Befehle. desktop.github.com → mit GitHub anmelden → File → Clone repository → Current branch → New branch → Änderungen committen → Publish branch → Create Pull Request.

🧩 VS Code

Hat Git eingebaut (Symbol „Source Control“ links). Branch unten links wechseln, Änderungen mit ✓ committen, mit „Sync“ hochladen.

⌨️ Kommandozeile

Git installieren. Beim ersten git push öffnet sich ein Browserfenster zur Anmeldung (Git Credential Manager).

Einmalig einrichten

git config --global user.name "Max M."
git config --global user.email "12345678+max-m@users.noreply.github.com"

Deine private noreply-Adresse findest du auf GitHub unter Settings → Emails („Keep my email addresses private“). So bleibt deine echte E-Mail geheim.

Der typische Ablauf

# 1. Repository einmalig herunterladen
git clone https://github.com/Yourworstdream/FSTAUD25.git
cd FSTAUD25

# 2. Neuesten Stand holen und eigenen Branch anlegen
git switch main
git pull
git switch -c thema/03-sensoren

# 3. Dateien bearbeiten, dann speichern (committen)
git add projekt/themen/03-sensoren.md
git commit -m "Sensoren: Grundlagen und Beispiele ergänzt"

# 4. Branch hochladen – danach den Link in der Ausgabe öffnen und den PR erstellen
git push -u origin thema/03-sensoren

Glossar

Repository (Repo)
Projektordner mit allen Dateien und der kompletten Änderungsgeschichte.
Commit
Ein gespeicherter Zwischenstand mit Beschreibung – wie ein Speicherpunkt im Spiel.
Branch
Eine Abzweigung, auf der man arbeitet, ohne den Hauptstand zu verändern.
main
Der Haupt-Branch mit dem offiziellen, geprüften Stand.
Pull Request (PR)
Vorschlag, die Änderungen aus einem Branch in main zu übernehmen.
Review
Prüfung eines PRs durch eine andere Person.
Merge
Das Zusammenführen eines Branches mit einem anderen.
Merge-Konflikt
Zwei Änderungen an derselben Stelle – ein Mensch muss entscheiden.
Issue
Ticket für eine Aufgabe, Frage, Idee oder einen Fehler.
Label
Farbiges Schlagwort an Issues und PRs, z. B. hilfe oder thema.
Collaborator
Person mit Schreibrechten im Repository.
Fork
Eigene Kopie eines fremden Repositorys. Brauchen wir nicht, weil ihr eingeladen werdet.
Clone
Kopie des Repositorys auf dem eigenen PC.
Push / Pull
Commits hochladen / neuesten Stand herunterladen.
Markdown
Einfache Schreibweise für formatierten Text (.md-Dateien).
GitHub Actions
Automatische Abläufe – bei uns berechnet eine Action den Live-Fortschritt.
GitHub Pages
Veröffentlicht Webseiten direkt aus einem Repository – so wie diese Seite.

Hilfe & FAQ

Du hängst fest? Frag in der Klasse oder erstelle ein 🆘 Hilfe-Issue.

Ich habe keine Einladungs-E-Mail bekommen.

Schau im Spam-Ordner nach oder öffne direkt die Einladungsseite. Steht dort nichts, hat dich der Admin noch nicht eingeladen – prüfe, ob dein Anmelde-Issue existiert.

GitHub will, dass ich das Repository „forke“.

Dann hast du noch keine Schreibrechte: Einladung annehmen (Schritt 2) und die Seite neu laden.

Mein Fortschritt wird nicht angezeigt.

Die Anzeige aktualisiert sich etwa eine Minute nach jeder Aktion, der Schritt „Im Team“ spätestens nach 10 Minuten. Prüfe außerdem: Hast du die Anmeldung wirklich mit Create abgeschickt? Heißt deine Steckbrief-Datei exakt wie dein Benutzername?

Beim Mergen steht „Review required“ oder „Merging is blocked“.

Das ist Absicht: Erst muss eine andere Person deinen PR mit Approve freigeben (Schritt 4).

Ich habe einen Fehler im PR – muss ich einen neuen machen?

Nein. Committe die Korrektur einfach auf denselben Branch, der PR aktualisiert sich automatisch.

Aus Versehen etwas Falsches gemerged – was jetzt?

Keine Panik, bei Git geht nichts verloren. Im gemergten PR gibt es unten den Knopf Revert: Er erstellt einen neuen PR, der die Änderung rückgängig macht.

Git fragt nach Benutzername und Passwort.

Das normale Passwort funktioniert bei Git nicht mehr. Nutze GitHub Desktop, oder installiere Git mit dem Git Credential Manager (bei Git für Windows automatisch dabei) – dann erfolgt die Anmeldung im Browser.

Darf ich Dateien von anderen bearbeiten?

Nur nach Absprache – und immer über einen PR, damit die Person ihn reviewen kann.

Für den Admin (@Yourworstdream)

Einmalige Einrichtung und die laufende Betreuung der Anmeldungen.

1. GitHub Pages einschalten (einmalig)
  1. Settings → Pages → bei Build and deployment als Source GitHub Actions auswählen.
  2. Actions → „Fortschritt & Webseite“ → Run workflow.
  3. Nach etwa einer Minute sind Anleitung und Live-Fortschritt unter yourworstdream.github.io/FSTAUD25 erreichbar. Ab dann aktualisiert sich alles automatisch.
2. Klassenkamerad:innen einladen
  1. Neue Anmeldungen findest du unter Issues mit dem Label „anmeldung“. Du wirst in jedem Anmelde-Issue erwähnt und bekommst eine Benachrichtigung.
  2. Settings → Collaborators → Add people → Benutzername eingeben → hinzufügen.
  3. Sobald die Einladung angenommen wurde, schließt die Action das Anmelde-Issue automatisch.
3. main schützen (empfohlen)
  1. Settings → Rules → Rulesets → New ruleset → New branch ruleset.
  2. Name main schützen, Enforcement status: Active. Bei Target branches → Add target → Include default branch.
  3. Anhaken: Restrict deletions, Require a pull request before merging (Required approvals: 1) und Block force pushes → Create.
  4. Tipp: Unter Bypass list „Repository admin“ hinzufügen, damit du im Notfall eingreifen kannst.
4. Weitere Einstellungen
  • Settings → General → Pull Requests → Automatically delete head branches anhaken.
  • In klasse.json lässt sich die Zahl der Plätze ändern und Konten ausblenden (z. B. das der Lehrkraft) – natürlich per Pull Request.
  • Der Fortschritt wird von .github/workflows/fortschritt.yml nach jeder Aktivität neu berechnet, zusätzlich alle 10 Minuten.
